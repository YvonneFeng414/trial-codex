SAP Generation Pipeline

How one protocol PDF becomes a Statistical Analysis Plan markdown. The batch driver (run_batch.sh) gives each PDF its own Codex session. Inside it, a primary agent writes the SAP and a separate reviewer agent checks it until the reviewer passes it. The harness accepts the result only if it passes a set of deterministic checks.

Protocol PDF→ Page-tagged text→ Evidence file→ SAP draft⇄ Reviewer cycles→ Lint→ Harness gates→ <id>.md

One job, step by step

1
Harness · run_batch.sh

Pick the PDF and admit the job

The driver finds every *_protocol*.pdf and turns its path into a job id, <journal>++<article-id>++<file-id>. --assignment-label can split the corpus across machines. A job starts only when enough quota and session time remain to finish it, judged from the p90 runtime of past jobs.

SKIP · <id>.md already exists
DEFERRED · not enough budget, or a .stop file exists from an earlier drain
2
Harness · tools/extract_pdf.py

Extract page-tagged text

The PDF's text layer is written to work/<id>.protocol.txt, with each page opened by a ===== PAGE N OF M ===== marker. Every SAP citation must use these page numbers, and M becomes the linter's --max-page.

UNSUPPORTED_SCAN · fewer than 20 characters per page on average. ocr_run_batch.sh adds an invisible text layer using Apple Vision OCR, and the PDF goes through the pipeline again.
3
Codex session · codex exec, multi-agent, workspace-write sandbox

Codex-in-the-loop: write, review, revise

The prompt gives the paths to the protocol text, evidence file, draft and review file, plus the page count, the verbosity (high) and the required reviewer model. AGENTS.md sets out the full workflow.

Primary agent gpt-5.6-terra · effort medium

  1. Read the protocol in fixed page ranges, from the first page to the last
  2. Write the evidence file, with one entry for each SAP field: facts, sources, absence searches, where each fact appears in the draft
  3. Write the draft SAP from the evidence file in the fixed 5-section template, with a citation on every block
  4. Check the draft for fields marked absent that another field answers
  5. Fix each finding in the evidence file and the draft
evidence + draft
findings (OPEN)

Reviewer subagent gpt-5.6-luna · fresh context

  1. Read the protocol itself instead of trusting the draft
  2. Cycle 1 lists every finding, each typed as OMISSION, CONTRADICTION, UNSUPPORTED, MISCLASSIFIED, CITATION, VERBOSITY or REGRESSION
  3. Later cycles only mark those findings RESOLVED or OPEN. The only new findings allowed are regressions the revision introduced
  4. Run a cross-field contradiction scan
  5. Add the final field checklist, then the line VERDICT: PASS

The reviewer only writes the review file and never edits the evidence or draft. The primary agent never writes the review file. The cycle 1 scope rule keeps the loop converging. Without it, each cycle could raise new findings, and the reviewer might never reach a verdict.

loop · repeats until the reviewer writes VERDICT: PASS
LIMIT_HIT · quota ran out partway. The other workers stop starting jobs, a progress snapshot is saved, and the retry count is unchanged
4
Agent, then harness · tools/lint_sap.py

Deterministic lint

The agent runs the linter until it passes, and the harness runs it again on its own.

  • Exactly the five ## sections and every ### section, in order
  • Every required bold field label is present
  • No banned hedges (likely, implied, presumably, typically, would be, standard practice, governed by SOPs) or placeholders
  • Every substantive block ends with *(Source: …)*, and every cited page is ≤ M
  • No field called absent while another field covers the same topic (for example, multiplicity)
5
Harness · acceptance gates

Accept or retry

The job is accepted only when all four checks pass. The draft is then moved to <id>.md and an OK row is added to _ledger.tsv.

OK · all gates pass
retry · the old review is archived as .attempt<n> and a fresh session starts. By default there is 1 retry, after which the job is marked FAIL

SAP Completeness Metric

A score from 0 to 1 for how many SAP template fields a generated markdown actually fills. An LLM judge reads one SAP, gives every field one of four classes, and the score is the weighted share of fields that apply to the trial. The judge reads only the SAP. It never sees the protocol, so the score measures completeness, not correctness.

How a file gets scored

1 · INPUT

One SAP markdown

For example, a file from Benchmark_merged/2/. Files already in the output TSV are skipped.

2 · JUDGE

codex exec

gpt-5.6-terra, effort low, read-only sandbox. AGENTS.md is not loaded, so the SAP-writing workflow plays no part.

3 · CLASSIFY

Label every field

filled, partial, not reported or not applicable. Citations are ignored.

4 · SCORE

Two ratios

overall_score over all fields, stat_score over the statistical sections only.

5 · OUTPUT

One TSV row

The row is format-checked, with one retry. It is appended to completeness_label2.tsv, which is then sorted by score.

Script: tools/eval_completeness.sh (currently checked in as .disabled). Each file runs in its own session. The judge's replies and logs are in completeness_label2.logs/.

What gets counted: the field map

Counted in stat_score and overall_score Counted in overall_score only

Narrative sections with no bullet fields (1.1, 2.4, 4.1, 4.2, 4.3, 5.5) count as one field each. With one sample-size block and one primary and one secondary outcome, the template has 74 fields, 48 of them statistical. Each extra outcome adds 4 fields and each extra sample-size block adds 18, so the denominator grows with the trial. Across label 2, the judge counted between 50 and 226 fields per SAP, with a mean of 97.

Four classes, three weights

filled

weight 1

Has substantive content.

partial

weight 0.5

Has some content, but says part of the field is not reported.

not_reported

weight 0

Says "Not reported in protocol" or "Deferred to SAP" and nothing more. A field missing from the file also counts here.

not_applicable

left out of the denominator

Cannot apply to this design, such as a non-inferiority margin in a superiority trial.

score = filled + 0.5 × partialfields − not_applicable

Rounded to 3 decimals. The same formula gives stat_score when only the statistical fields are counted (2.3–2.6, 3.1–3.3, 5.3–5.7), and overall_score when every field is counted.

Reading the score

  • It measures completeness, not correctness. The judge never opens the protocol. A filled field might be wrong, and a "Not reported" field might be accurate if the protocol really is silent. The lint and reviewer gates in the generation pipeline cover grounding.
  • Low scores often reflect the protocol. The usual gaps (per-protocol set, sample-size software, missing-data assumptions) are things many protocols never state.
  • The counts come from the model. The judge counts the fields itself, so the denominator can vary between runs and between files. A malformed reply is retried once and then dropped.
  • Not applicable leaves the denominator. If the judge marks a field not applicable when it should be not reported, the score goes up.
